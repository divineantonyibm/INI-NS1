01

Plan and Execute DNS Changes

Intent-to-execution DNS orchestration with multi-agent NOC

Scenario

An enterprise needs to execute a complex emergency traffic migration — shedding 40% of traffic from an overloaded EU data center to US East and APAC while maintaining regional data compliance. Manually editing records across multiple zones risks misconfiguration. The goal is to execute the multi-zone migration without manual record edits.

How INI & NS1 contribute

IBM NS1 Connect

Executes dynamic Filter Chain weight updates, record modifications, and Pulsar steering overrides; provides instant sub-second propagation across all global PoPs.

IBM Network Intelligence

Takes the engineer's intent from INI's Chat Assistant and drafts the change with a multi-agent system: Reasoning Agent devises a step-by-step traffic shifting plan; RAG Agent checks enterprise change policies and runbooks; Function-Calling Agent constructs atomic NS1 mutation payloads and rollback scripts.

Mechanisms NOC AI Multi-Agent RAG Policy Verification Function-Calling API Atomic Rollback Human-in-the-Loop

Moments of truth

  • The approver sees the reasoning trace, proposed action and rollback plan together before saying yes.
  • A clear rollback plan, with approval to use it, removes fear of executing.

Success measures

  • Change lead time
  • Rollbacks triggered vs. incidents avoided
  • Changes with complete audit trail

Expected impact

Expected: faster, less error-prone changes with a full audit trail (targets to be validated).

How this use case is done in NS1 Connect today, before INI. Checked against the IBM NS1 Connect documentation.

02

Build Advanced Traffic Steering

Telemetry-guided Filter Chain & Pulsar policy synthesis

Scenario

Architects configuring multi-CDN and hybrid-cloud steering must balance latency performance, committed transit billing commitments, data sovereignty laws (GDPR), and origin capacity limits. The goal is to turn a business routing goal into a Filter Chain that meets all of these constraints.

How INI & NS1 contribute

IBM NS1 Connect

Provides patented modular Filter Chain engine, Pulsar real-user monitoring (RUM) telemetry feeds, and real-time DNS decisioning at global edge points.

IBM Network Intelligence

Analyzes historical network telemetry, multi-cloud egress costs, transit latency curves, and application capacity models to recommend a Filter Chain, choosing the filters, their order and their thresholds; saves patterns as reusable INI Skills that encode standard policies.

Mechanisms Filter Chain Optimization Pulsar RUM Feeds Reusable Skills Intent Decomposition

Moments of truth

  • Seeing the draft chain justified by real telemetry rather than generic advice.
  • Saving a design turns one design into a team standard.

Success measures

  • Design time from goal to approved chain
  • Latency change after rollout
  • Saved designs reused across squads

Expected impact

Expected: lower latency, controlled transit cost and consistent steering patterns across squads (targets to be validated).

How this use case is done in NS1 Connect today, before INI. Checked against the IBM NS1 Connect documentation.

Designing a Filter Chain and Pulsar steering in NS1 Connect

The architect picks and orders the filters, sets answer metadata and connects monitors or Pulsar jobs. Filters run from top to bottom, so order is a design decision made by hand.

03

Verify a Designed Filter Chain Before Go-Live

Capacity and TTL safety check for a new multi-CDN Filter Chain

Scenario

Before go-live, the DevOps squad must make sure that a TTL caching side effect or a Filter Chain logic error does not push too much traffic to a smaller secondary datacenter and overload it. The goal is to confirm the designed Filter Chain is safe before it reaches production.

How INI & NS1 contribute

IBM NS1 Connect

Holds the Filter Chain, answer metadata and record TTLs, and exposes them with query telemetry so INI can build a digital twin of the proposed setup without touching the live record (proposed).

IBM Network Intelligence

Builds a digital twin of the designed chain and its origins, replays recent query telemetry through it including TTL caching effects, and compares predicted load with each origin's capacity; reports overloaded origins and chain logic errors with explainable reasoning via View reasoning, and suggests fixes.

Mechanisms Digital Twin Simulation Predictive Replay Capacity Check TTL Caching Analysis Explainable AI CI/CD Gate Integration

Moments of truth

  • The predicted load on the secondary datacenter is shown before anything is deployed.
  • INI points to the exact weight, filter or TTL that causes the overload.

Success measures

  • Overload risks caught before release
  • Iterations to reach a passing check
  • Capacity incidents after go-live

Expected impact

Expected: fewer capacity incidents after Filter Chain rollouts and faster approvals (targets to be validated).

How this use case is done in NS1 Connect today, before INI. Checked against the IBM NS1 Connect documentation.

04

Interpret DNS Telemetry & Troubleshoot Issues

Cross-layer DNS & underlay telemetry correlation

Scenario

When a critical service experiences localized resolution failures, operators struggle to determine whether the fault lies in NS1 health-check flapping, CDN edge degradation, authoritative nameserver rate-limiting, or an upstream ISP BGP transit route flap. The goal is to find the real root cause in seconds and avoid chasing the wrong layer.

How INI & NS1 contribute

IBM NS1 Connect

Streams real-time query metrics, Pulsar active/passive latency feeds, Filter Chain execution logs, and health monitor state transitions via MCP telemetry connectors.

IBM Network Intelligence

Applies Quantile and Prophet time-series foundation models to detect anomalous baseline shifts; correlates DNS anomalies with BGP routing flaps and interface congestion; auto-generates root-cause hypotheses to pinpoint the root cause immediately.

Mechanisms Time-Series AI MCP Telemetry Ingest Semantic Correlation Pulsar RUM watsonx Foundation Models

Moments of truth

  • One grouped incident replaces an alert storm.
  • A cross-layer root cause answers the "DNS or network?" question immediately.

Success measures

  • MTTD / MTTI
  • Alerts grouped per incident
  • Escalations with correct owner first time

Expected impact

Expected: faster detection and root-cause identification with fewer duplicate alerts (targets to be validated).

How this use case is done in NS1 Connect today, before INI. Checked against the IBM NS1 Connect documentation.
