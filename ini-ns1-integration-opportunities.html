IBM Network Intelligence × NS1 Connect

Integration
Opportunities

A structured analysis of how IBM Network Intelligence and IBM NS1 Connect can be integrated to create outcomes neither product achieves alone — spanning traffic protection, intelligence sharing, agentic automation, and unified observability.

Integration Use Cases · 12 Scenarios

Overview

Two products.
One closed loop.

INI knows what is wrong and why at the network layer. NS1 controls where traffic flows at the DNS layer. The gap between those capabilities — detect a degradation, then act on it via DNS — is what every use case in this document bridges.

IBM Network Intelligence (INI)
An AI-native SaaS platform that transforms multi-vendor network telemetry into anomaly detections, root-cause hypotheses, and agentic remediation. Core strength: understanding what is wrong and why — across IP and RAN domains — using time-series foundation models, NOC AI agents, and a RAG knowledge base.
IBM NS1 Connect
An authoritative DNS and traffic steering platform that controls where traffic flows — routing users to the fastest, most available, and most cost-effective endpoint at the moment of each DNS query. Core strength: programmable, real-time traffic management via Filter Chains, health monitors, and Pulsar RUM data.

Four technical integration pathways

01
OpenAPI / REST
Both products expose fully documented REST APIs. INI can call NS1's record and monitor APIs; NS1 can receive INI anomaly signals via webhook or polling.
02
MCP Server Protocol
INI natively supports MCP server integration. NS1 query telemetry, routing decisions, and anomaly policies can be fed into INI as an MCP-connected data source.
03
Agent-to-Agent (A2A)
INI's agentic framework supports A2A protocol. An NS1 automation agent can act as an external agent in INI's multi-agent remediation workflow.
04
ITSM Ticket + Skills
INI auto-creates ITSM tickets with remediation plans. NS1 DNS change steps can be embedded as Skills in INI's knowledge base, included in every generated ticket.
INI × NS1 Connect — Integration Opportunities 1

Category 01

Traffic
Protection

INI detects degradation patterns early — often before a server fails a health check. These use cases exploit that early-warning capability to steer DNS traffic away from at-risk infrastructure proactively.

01 Predictive Failover
AI-Predicted Pre-emptive DNS Failover
NS1's health monitors detect endpoint failures reactively — after an endpoint stops responding. INI's time-series models identify subtle degradation patterns (rising latency, packet loss trends, CPU saturation gradients) minutes to hours before a service fails its health check. Integrating the two creates a pre-emptive failover loop: INI fires a warning when a server is on a degradation trajectory; NS1 adjusts the Filter Chain before it fails.
INI
Time-series anomaly detection identifies degrading endpoints 15–120 minutes before failure. NOC AI agent generates a root-cause hypothesis and triggers an API call with recommended DNS action.
NS1
Filter Chain updated via API to set the degrading endpoint's weight to zero or assign a lower priority tier. Traffic shifts to healthy alternatives before the endpoint fails its health check.
Mechanism INI OpenAPI → NS1 REST INI NOC Agent → A2A → NS1 DNS Agent INI Skill: adjust-filter-chain-weight

Outcome: Customer-impacting failover events are reduced. Traffic exits before the server collapses, eliminating the window where users hit a failing endpoint waiting for DNS TTL to expire.

02 DDoS Correlation
Network-Layer DDoS Signal → DNS Traffic Diversion
INI monitors the underlying network — detecting volumetric anomalies, sudden traffic spikes, and infrastructure saturation that precede or accompany an attack. By sharing attack signals, INI sees the network being hit while NS1 simultaneously changes DNS answers to divert users to unaffected regions or a scrubbing centre endpoint.
INI
Anomaly detection flags abnormal traffic volume across IP domain routers. Root-cause hypothesis identifies attack type and affected PoP/region. Alert triggers API call to NS1 with affected region identifier.
NS1
Geographic filter in the Filter Chain overrides routing for the affected region — diverting queries to clean-pipe endpoints or scrubbing infrastructure.
Mechanism INI alert webhook → NS1 API geo-filter update INI Dashboard + NS1 Insights joint monitoring

Outcome: Unified attack response across network and DNS layers. Time from attack detection to traffic diversion compresses from minutes (manual) to seconds (automated).

03 RAN Degradation
RAN Site Degradation Triggering CDN Re-steering
When INI detects a RAN site degradation — such as a base station with rising packet loss or a backhaul congestion event — NS1 can redirect content delivery for that geographic region to a CDN PoP with better connectivity, improving end-user quality of experience during network degradation events.
INI
RAN domain anomaly detection identifies degraded base station or backhaul segment. Device-level analysis provides geographic identifier (site ID, lat/lon, region code) of the affected area.
NS1
Subnet or geographic Filter Chain rule updated to route mobile subscribers in the affected area to an alternative CDN PoP with better backhaul connectivity.
Mechanism INI RAN anomaly → region code → NS1 geo-filter API INI Grounding Doc: RAN-region-to-CDN mapping

Outcome: Content delivery QoE preserved during RAN degradation events. Mobile users in an affected cell area are automatically routed to a better-performing CDN without manual intervention.

INI × NS1 Connect — Integration Opportunities 2

Category 02

Intelligence
Sharing

INI and NS1 each collect a distinct signal stream. These use cases connect those streams — giving INI richer context for root-cause analysis and giving NS1 deeper network telemetry to drive better routing decisions.

04 DNS Telemetry into INI
NS1 DNS Query Telemetry as an INI Data Source
NS1 Insights produces detailed DNS query analytics — query volumes by region, resolution latencies, routing decisions, and anomaly flags. Feeding NS1 telemetry into INI as an MCP-connected data source gives INI's AI models a complete picture: both the network-side anomaly and the application-side DNS impact, enabling richer root-cause correlations and faster MTTR.
INI
Ingests NS1 DNS telemetry as a new data stream via MCP Server integration. Correlates DNS resolution anomalies with network-layer events (e.g., CNAME resolution failures align with router interface drops on the same AS path).
NS1
Streams DNS Insights analytics — query volume changes, routing decision logs, health monitor state changes — as time-series metrics to INI's data pipeline via MCP or REST API.
Mechanism NS1 Insights API → INI MCP Server INI device triplet: NS1-zone / record / query-volume

Outcome: INI root-cause hypotheses include DNS-layer evidence. Engineers receive tickets with complete end-to-end causality: network fault → DNS consequence → user impact — in a single ticket.

05 Pulsar + INI Latency Fusion
Fusing Pulsar RUM Data with INI Network Latency Models
NS1 Pulsar collects real-user latency measurements from browsers — the actual application-layer experience. INI monitors network-layer latency across routers and links. Correlating both datasets makes it possible to distinguish between "network is slow" and "CDN is slow" — a distinction that determines whether the right remediation is a network change (INI) or a DNS re-steer (NS1).
INI
Provides network-layer latency telemetry from routers, switches, and WAN links. INI's AI determines whether observed application latency is attributable to network infrastructure or to the CDN/application tier.
NS1
Pulsar RUM data provides real-user CDN/endpoint latency per region. When the CDN is the driver, NS1's Filter Chain is updated. When the network is the driver, NS1 defers to INI remediation.
Mechanism Pulsar latency API → INI data pipeline INI reasoning agent: CDN vs. network attribution Conditional NS1 Filter Chain update via A2A

Outcome: Smarter remediation routing. The AI correctly decides whether to fix the DNS (NS1) or fix the network (INI) — eliminating false remediations where DNS is re-steered when the root cause is actually a router in the path.

06 Topology Context
Network Topology Context Enriching NS1 Routing Decisions
NS1's routing decisions are based on DNS-layer signals — health checks, latency probes, RUM data. They lack awareness of the underlying network topology: BGP AS paths, router utilisation, link capacity, and physical site interconnections. Exposing INI's semantic network context to NS1's Filter Chain engine means DNS routing can factor in network-layer capacity and congestion — not just endpoint availability.
INI
Semantic network context provides real-time topology data: which links are congested, which routers are approaching capacity, which AS paths have higher-than-normal latency. Exported via API as structured metadata tags per endpoint or region.
NS1
Record metadata fields and custom Filter Chain logic consume INI-provided network health tags — steering traffic away from endpoints that are "up" but reachable via a congested network path.
Mechanism INI topology API → NS1 record metadata update NS1 custom filter: network-congestion-score tag

Outcome: DNS routing that reflects the actual network, not just surface-level endpoint health. Users are steered to endpoints with genuinely clean network paths — combining the best of application-layer and network-layer observability.

INI × NS1 Connect — Integration Opportunities 3

Category 03

Agentic
Automation

INI's NOC AI agents can detect, investigate, and execute remediation. NS1's API enables programmatic DNS change. These use cases describe fully automated closed-loop scenarios — with or without human approval.

07 Autonomous Mode
INI NOC Agent Autonomously Updates NS1 Filter Chains
For well-understood, repetitive network incidents with pre-validated remediation plans, INI operates in Autonomous mode — detecting the anomaly, identifying the root cause, and executing the NS1 DNS change without human intervention. An INI Skill encodes the NS1 API call sequence as a reusable workflow step invoked automatically by the NOC AI agent.
INI
Autonomous mode NOC agent detects anomaly, generates hypothesis, selects the "DNS-failover" Skill, and executes it — calling the NS1 API to update the record and logging the action to the ITSM ticket. No human in the loop.
NS1
REST API accepts programmatic record and Filter Chain updates from the INI agent. The change propagates globally in under 20 seconds. NS1 Insights confirms traffic re-routing success and feeds confirmation back to INI.
Mechanism INI Skill: ns1-update-filter-chain INI Autonomous mode → NS1 REST API NS1 confirmation → INI ITSM ticket close

Outcome: Zero-touch DNS failover for pre-approved incident types. The NOC team wakes up to a ticket showing: anomaly detected → DNS updated → traffic rerouted → incident auto-resolved.

08 Assistant Mode
Human-in-the-Loop DNS Change Approval Workflow
For complex, high-risk, or novel incidents, INI's Assistant mode surfaces the full remediation plan — including the proposed NS1 DNS changes — for human review before execution. The NOC operator reviews the AI's root-cause analysis and the specific NS1 API calls it intends to make, approves with a single click in the ITSM ticket, and the INI agent executes the DNS change.
INI
Assistant mode generates an ITSM ticket with root-cause hypothesis, reasoning chain, and a pre-flight validated NS1 API payload. Human approves or edits. On approval, INI agent executes the NS1 call and logs the outcome.
NS1
Receives the validated API call from INI upon human approval. Because the payload was pre-validated, the change applies immediately with zero DNS configuration errors — no typos, no missing fields.
Mechanism INI ITSM ticket + NS1 payload preview Human approval → INI agent → NS1 REST API INI "View reasoning" for audit trail

Outcome: DNS changes for complex incidents happen 5–10× faster than fully manual workflows — with the same human accountability. Operators approve a pre-validated, AI-authored change rather than authoring it from scratch under pressure.

09 Capacity Management
Predictive DNS Load Balancing Based on INI Capacity Forecasts
INI's time-series models detect capacity trends — gradual saturation of routers, rising utilisation on key infrastructure links, or seasonal traffic patterns predicting demand spikes. These forecasts can proactively adjust NS1's weighted load balancing before saturation occurs, redistributing DNS traffic away from infrastructure trending toward its capacity limit.
INI
Long-term time-series analysis forecasts which data centre or network region is trending toward saturation over the next 1–12 hours. Publishes a capacity score per region via API — refreshed every N minutes.
NS1
Weighted Shuffle filter in the Filter Chain consumes INI's capacity scores as weights — dynamically shifting traffic proportions across regions in real time as the forecast changes. No manual weight tuning required.
Mechanism INI capacity forecast API → NS1 weighted filter update Scheduled INI agent: capacity-to-weight translation

Outcome: Proactive load balancing that prevents network saturation events before they become outages. Traffic is redistributed gradually and automatically — not in a sudden failover spike when a threshold is breached.

INI × NS1 Connect — Integration Opportunities 4

Category 04

Observability & Operational Efficiency

These use cases improve operational visibility and reduce toil — combining INI's deep network telemetry with NS1's DNS-layer observability for unified incident context and more efficient team workflows.

10 Unified Incident Context
Single ITSM Ticket with Network + DNS Evidence
Today, a production incident typically generates separate tickets or alerts in network monitoring tools and DNS management tools — engineers must manually correlate them. By integrating INI's ITSM ticket generation with NS1's Insights data, a single auto-generated ticket contains both the network-layer root cause and the DNS-layer impact: which endpoints were removed, how traffic shifted, and the user-facing consequence.
INI
Generates ITSM ticket with network root-cause hypothesis, affected devices, and anomaly timeline. NOC agent queries NS1 Insights API to append DNS impact data to the same ticket before filing it.
NS1
NS1 Insights API provides: which endpoints failed health checks, how Filter Chain routing changed, query volume impact by region, and whether failover was triggered.
Mechanism INI RAG: NS1 Insights API as grounding context INI ITSM enrichment: DNS impact section in ticket body

Outcome: Incident tickets are complete on arrival. On-call engineers see the full story — network fault, DNS consequence, traffic impact — in one place. Post-incident reviews are faster and more accurate.

11 Change Risk Detection
INI Monitors Network Impact of NS1 DNS Changes
NS1 DNS changes — especially large-scale GSLB weight updates, geo-routing policy changes, or major failover events — can cause significant traffic shifts that affect downstream network infrastructure. By tagging planned NS1 DNS changes as events in INI's timeline, INI's anomaly detection can distinguish between anomalies caused by the DNS change and independent network faults, reducing false-positive alerts during change windows.
INI
Ingests NS1 change events as markers in the INI observation timeline. During and after a DNS change window, anomaly detection is calibrated to suppress expected traffic shifts while still alerting on genuine faults unrelated to the change.
NS1
Publishes DNS change events (record updates, Filter Chain modifications, health monitor state changes) via webhook or API — providing INI with the timing and scope of each change for contextual anomaly suppression.
Mechanism NS1 change webhook → INI event timeline INI contextual anomaly suppression during change windows

Outcome: Fewer false-positive alerts during DNS changes. NOC operators are not flooded with traffic-shift alerts every time a planned DNS change redistributes load — only genuine faults surface during and after change windows.

12 NOC Chat Assistant
Natural Language DNS + Network Queries via INI Chat
By connecting NS1's data as a grounding source and tool in the INI chat, operators can ask cross-domain questions like "Why are users in Europe experiencing high latency?" and receive a synthesised answer spanning both the network layer (INI: router interface congestion on EU peering links) and the DNS layer (NS1: Pulsar data shows UK users being routed to US CDN endpoints due to a stale geo-filter).
INI
Chat assistant with chain-of-thought reasoning queries both INI's own anomaly data and NS1's Insights API as a registered tool. Synthesises a unified answer covering network and DNS layers. "View reasoning" shows which data sources were consulted.
NS1
NS1 REST API and Insights data are registered as Tools in INI's function-calling agent. INI chat can call NS1 in real time — retrieving current routing decisions, health monitor states, and query analytics on demand.
Mechanism NS1 API registered as INI Tool Management integration INI RAG: NS1 docs as grounding document INI Chat: cross-domain natural language queries

Outcome: A single pane of glass for network + DNS questions. NOC operators no longer need to context-switch between INI's dashboard and NS1's portal — the AI assembles the answer from both systems on demand.
